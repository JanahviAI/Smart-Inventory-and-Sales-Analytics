# Team Implementation Plan — Smart Inventory and Sales Analytics Platform

## Purpose and working rule

This document is the shared contract for all four members. Read it before asking an AI agent to code. The objective is one integrated system, not four independent demos.

**Repository:** https://github.com/JanahviAI/Smart-Inventory-and-Sales-Analytics

**Core journey:** CSVs → NiFi landing → Airflow DAG → PostgreSQL staging → validation/cleaning → trusted PostgreSQL tables → Parquet → DuckDB analytics → reorder recommendations → mock FastAPI service → reverse-ETL audit. Parallel streaming journey: producer → Redpanda → consumer → PostgreSQL event/inventory update → dashboard.

**Non-negotiable:** no invented metrics, screenshots, benchmark numbers, or success claims. Everything reported must come from an actual execution.

## 1. Decisions to freeze before coding

Have one short team meeting. Write the decisions in `docs/INTERFACES.md` and `docs/DATA_DICTIONARY.md`.

1. Source inputs: `sales.csv`, `products.csv`, `inventory.csv`.
2. Sales business key: use `(order_id, product_id)` only if one product can appear at most once per order. Otherwise add `order_line_id` and use that as the key.
3. Dates: choose and document a consistent ISO date/time format. Streaming timestamps must include timezone.
4. Invalid data: record it in `rejected_records` with a reason; do not silently drop it.
5. Storage: PostgreSQL is the operational source of truth; plain Parquet is the analytics export. Delta Lake is out of scope until core features work.
6. Streaming stock rule: an accepted sale event decrements stock by quantity. Duplicate event IDs cannot decrement stock twice. If stock would become negative, reject and record the reason.
7. Reorder rule: if `current_stock <= reorder_level`, recommend `max(0, target_stock - current_stock)`. Define target stock (for example, twice the reorder level) and handle zero reorder level.
8. Reverse ETL: local FastAPI mock service; use idempotent `PUT /recommendations/{recommendation_key}` and record every outcome in `reverse_etl_audit`.
9. NiFi/Airflow handoff: NiFi writes to shared `data/landing/`; Airflow detects required files using a scheduled check/sensor. Do not claim a direct event trigger unless built.
10. Agree on Python/Docker versions, image tags, ports, health checks, and environment variables before the Compose file is finalized.

Do not start independent AI coding until everyone agrees to these decisions.

## 2. The complete data lifecycle

### A. Raw data
Keep small, deterministic demo inputs under `data/source/`. A script can generate larger reproducible benchmark data. NiFi writes copies/routes into `data/landing/`; the source files should not be silently overwritten.

- `sales.csv`: `order_id`, `order_date`, `product_id`, `quantity`, `unit_price`, plus `order_line_id` if needed.
- `products.csv`: `product_id`, `product_name`, `category`, `supplier_id`.
- `inventory.csv`: `product_id`, `current_stock`, `reorder_level`.

### B. NiFi ingestion
Create a visible NiFi flow that reads the three source files and routes them to the shared landing directory. Keep business validation in the ETL layer. Make sure NiFi and Airflow mount the same volume. Verify files actually arrive and are complete before Airflow reads them.

### C. Airflow orchestration
DAG ID: `retail_batch_pipeline`. Tasks, in order:

1. `check_input_files`
2. `load_staging`
3. `validate_and_clean`
4. `export_clean_data`
5. `calculate_analytics`
6. `generate_reorder_recommendations`
7. `sync_recommendations`
8. `reconcile_pipeline`

The DAG imports reusable functions from `src/`; it must not duplicate business logic. Set safe retries, timeouts, meaningful logs, run IDs, and failure behavior. Failed prerequisites block dependent tasks.

### D. Staging and quality
Load raw values into staging. Validate required columns, types, date formats, foreign keys, quantity/price/stock constraints, and duplicates. Upsert valid data to trusted tables. Write invalid rows to `rejected_records` with source, raw row/payload, reason, and run ID.

**Required result:** trusted tables only contain accepted records, rejected rows can be inspected, and re-running the same batch does not duplicate trusted sales.

### E. Parquet and analytics
Export cleaned data to `data/processed/`. Use DuckDB SQL for revenue/units, daily/category rollups, top products, and low-stock inventory. If Polars is used for comparison, run exactly the same computation on the same data and verify equivalent output.

**Required result:** analytics are generated by scripts/queries and made available to the dashboard as actual data.

### F. Reorder recommendations
Use the agreed deterministic formula. Store product, current stock, reorder level, recommended quantity, reason, timestamp, and stable recommendation key in `reorder_recommendations`.

**Required result:** the same input state yields the same recommendation keys and values.

### G. Reverse ETL
Send recommendations to the mock FastAPI service. Validate payloads and upsert by stable recommendation key. Store each attempt, response status, and outcome in `reverse_etl_audit`. Test a valid payload, repeat request, invalid payload, and API failure/retry.

**Required result:** trace one recommendation from analytical output to request, response, and audit row. Describe this honestly as a mock integration, not a real ERP.

### H. Streaming
Producer sends JSON events to Redpanda topic `sales.events`. Consumer validates and deduplicates by `event_id`, persists accepted events to `inventory_events`, and applies the stock rule. Invalid and duplicate attempts must be visible.

**Required result:** count an event as processed only after it is consumed and persisted. Measure publish-to-database latency; do not invent a latency result.

### I. Dashboard
Streamlit reads real PostgreSQL/API/result data. Suggested tabs:
- Overview: latest pipeline status, sales/revenue, low-stock products.
- Pipeline: run history and outcomes.
- Data Quality: accepted/rejected/duplicate counts and reasons.
- Analytics: daily/category sales, top products.
- Streaming: event counts and measured latency.
- Reverse ETL: recommendations and API audit.
- Benchmark: actual benchmark results only.

Show clear empty/error states if a service is down. Do not hardcode metrics.

### J. Reconciliation
At batch end, verify counts and required outputs. Save a generated run summary. A run is not successful if required outputs are missing or required checks fail.

## 3. Shared function contracts

Do not independently rename these functions or their output fields without team agreement.

```python
# src/etl/staging.py
def load_staging(run_id: str) -> dict:
    """Load required landing files into staging tables."""

# src/etl/validation.py
def validate_and_clean(run_id: str) -> dict:
    """Validate, deduplicate, upsert trusted data, and log rejects."""

# src/etl/export.py
def export_clean_data(run_id: str) -> dict:
    """Export trusted datasets to Parquet and return paths/counts."""

# src/analytics/queries.py
def calculate_analytics(run_id: str) -> dict:
    """Calculate agreed sales and inventory metrics."""

# src/analytics/recommendations.py
def generate_reorder_recommendations(run_id: str) -> dict:
    """Store deterministic recommendations and return counts."""

def sync_recommendations(run_id: str) -> dict:
    """Call mock API and record outcomes in reverse_etl_audit."""

# src/streaming/consumer.py
def process_inventory_event(event: dict) -> dict:
    """Validate/deduplicate/persist event and apply inventory rule."""
```

Each returns a summary object with at least `status` (`success`, `failed`, or `partial`), `processed`, `failed`, and `message`. Add useful fields such as `rejected`, `run_id`, `duration_seconds`, and output paths. This is an interface contract, not an example of actual results.

## 6. Implementation order

### Phase 0 — Shared contract
All four agree on keys, schemas, event/API payloads, recommendation formula, file paths, ports, and versions. Commit `docs/INTERFACES.md`.

### Phase 1 — Foundation
Person 2 leads schema, deterministic source CSVs, environment config, and PostgreSQL. All members review before building against it.

Person 3 implements queries, recommendations, mock API, and audit. Verify against independent SQL/API calls.

Person 4 builds producer/consumer and proves accepted, duplicate, and invalid behavior.

### Phase 5 — NiFi and dashboard
Person 1 proves NiFi-to-landing. Person 4 wires Streamlit to actual stored results.

### Phase 6 — Integration freeze
Stop adding features. Run acceptance tests from a clean state, fix integration problems, capture evidence, and rehearse explanations.

## 7. Acceptance test matrix

Write exact commands and expected behavior in `docs/ACCEPTANCE_TESTS.md`.

| ID | Scenario | Required outcome |
|---|---|---|
| AT-01 | Clean batch | Trusted rows, Parquet, analytics, recommendations, audit exist |
| AT-02 | Missing input | Airflow fails clearly; dependent tasks do not run |
| AT-03 | Invalid quantity/date/product | Rejection with reason; trusted tables stay clean |
| AT-04 | Identical batch rerun | No duplicate trusted sales |
| AT-05 | Valid event | Persisted and stock changes once |
| AT-06 | Duplicate event ID | No second stock change |
| AT-07 | Invalid event | Visible rejection |
| AT-08 | Valid reverse ETL | API upsert succeeds and audit row exists |
| AT-09 | Repeated recommendation | No duplicate logical recommendation |
| AT-10 | API failure/invalid payload | Outcome logged; retry behavior visible |
| AT-11 | Dashboard reconciliation | Counts match SQL/API |
| AT-12 | Benchmark (if included) | Same workload, equivalent output, recorded conditions |

Define expected outcomes independently before AI writes the tests. A test passing is not proof the test expectation itself is correct; another teammate should review it.

## 8. Git and AI workflow

- Use feature branches, e.g. `feat/etl-quality`, `feat/airflow-dag`, `feat/analytics-api`, `feat/streaming-dashboard`.
- Open PRs; do not overwrite teammates' work.
- Every PR states files changed, commands run, tests run, actual output, and any contract changes.
- Never commit `.env`, credentials, virtual environments, database volumes, or huge generated datasets.
- Ask AI to inspect existing files first, change only owned files, obey shared contracts, add tests, and report exact commands/results. Do not accept unexecuted tests as passing.
- If a shared interface must change, agree first and update docs/tests before dependent modules are changed.

## 9. Final definition of done
